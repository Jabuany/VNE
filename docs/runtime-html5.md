# Runtime HTML5 · propuesta del BLOQUE 9

## Comparativa y orden de implementación

| Plataforma | Motor y adaptador propuestos | Base comprobada | Límites que requieren pruebas |
| --- | --- | --- | --- |
| Android | Android WebView del sistema, Activity Kotlin no exportada y AndroidX WebKit para la carga local y los perfiles. Dart controla la sesión. | Android 15 (API 35) con proveedor `com.google.android.webview` 157.0.8103.50. El APK mantiene API mínima 24. AndroidX WebKit 1.18.0 es una versión estable candidata, bajo Apache-2.0. | Detectar las capacidades del proveedor antes de iniciar. Verificar perfiles múltiples, carga HTTPS interceptada con red bloqueada, audio, confinamiento y ciclo de vida en el teléfono. API 24 es el piso del APK. La compatibilidad del runtime depende del proveedor. [AndroidX WebKit](https://developer.android.com/jetpack/androidx/releases/webkit) · [Licencia AndroidX](https://android.googlesource.com/platform/frameworks/support/+/androidx-main/LICENSE.txt) |
| Linux | WebKitGTK 4.1 en un ejecutable auxiliar GTK 3, con ventana separada y una sesión por proceso. | Debian 13.8 amd64, WebKitGTK **2.54.3** y bubblewrap **0.12.0** instalados. El paquete de desarrollo compatible está disponible en el repositorio de seguridad. | Probar la ejecución con los dos niveles de confinamiento activos. Verificar Wayland, codecs, recursos con rangos, perfiles y cierre. Primera base de validación propuesta: Debian 13 amd64, ABI WebKitGTK 4.1 y versión con correcciones de seguridad al día. [Paquete Debian](https://packages.debian.org/trixie/libwebkit2gtk-4.1-0) · [Avisos WebKitGTK](https://webkitgtk.org/security.html) |

Se propone **Android primero**. El teléfono ya está disponible y el sistema aporta WebView. Una Activity de pantalla completa evita el coste y la complejidad de componer una vista nativa con Flutter durante la reproducción. La alternativa es una Platform View, que facilita superponer controles Flutter y requiere medir rendimiento y accesibilidad. Para Linux, una ventana auxiliar respeta la separación de proceso. Un navegador completo externo reduciría la integración inicial y dificultaría imponer el perfil, las políticas de navegación y el cierre desde VNE. WebKitGTK 6.0 se evaluaría si el auxiliar migra a GTK 4. [Platform Views en Android](https://docs.flutter.dev/platform-integration/android/platform-views) · [Migración a WebKitGTK 6.0](https://webkitgtk.org/reference/webkit2gtk/2.39.91/migrating-to-webkitgtk-6.0.html)

WebKitGTK y sus componentes tienen avisos de BSD, LGPL y otras licencias, según el inventario Debian. Bubblewrap se distribuye principalmente bajo LGPL-2.1 o posterior. Se propone enlazar los paquetes mantenidos por Debian y revisar sus avisos para la distribución. Para compilar el auxiliar, la simulación actual de `libwebkit2gtk-4.1-dev` añadió 13 paquetes, 2,2 MB de descarga y 13,9 MB de disco. Los enlaces se revisarán al preparar el paquete. La propuesta de AndroidX añade una biblioteca Kotlin/Java al APK y reutiliza el proveedor del sistema. El incremento de tamaño se medirá al compilar. [Desarrollo en Debian](https://packages.debian.org/trixie/libwebkit2gtk-4.1-dev) · [Bubblewrap](https://github.com/containers/bubblewrap)

## Acceso local y confinamiento

1. **Resolver la fuente antes del arranque.** Abrir la URI importada con acceso de lectura y validar cada petición dentro de la raíz seleccionada. Reutilizar la infraestructura SAF y el acceso confinado de Linux. Comprobar la entrada otra vez, en especial para referencias que pudieron cambiar. Un recurso inexistente o fuera de raíz devuelve un error controlado. Los recursos se entregan por bloques con MIME correcto. Deben validarse las rutas relativas y los rangos para recursos multimedia antes de anunciar compatibilidad.
2. **Android.** Servir los contenidos desde un origen HTTPS sintético distinto por juego, mediante `WebViewAssetLoader` y un manejador de recursos acotado. Las solicitudes ajenas al origen o sin coincidencia reciben un rechazo explícito. Desactivar acceso mediante `file:` y `content:`, contenido mixto, ventanas extra y depuración de WebView en distribución. Bloquear cargas de red y probarlo aun en APK debug, que tiene permiso de Internet para el servicio de herramientas. Validar `MULTI_PROFILE` y asignar el perfil antes de navegar. Si el proveedor no permite el aislamiento previsto, devolver un diagnóstico y detener el arranque. [Carga local en WebView](https://developer.android.com/develop/ui/views/layout/webapps/load-local-content) · [Ajustes de WebView](https://developer.android.com/reference/android/webkit/WebSettings) · [Perfiles de WebView](https://developer.android.com/reference/androidx/webkit/ProfileStore)
3. **Linux.** Servir un esquema del auxiliar con origen estable por juego y un contexto con rutas de datos y caché privadas. Verificar que las funciones web requeridas traten ese esquema como origen apto. Activar y comprobar el sandbox del proceso web. Ejecutar el auxiliar en un espacio de red aislado con Bubblewrap y montajes mínimos: juego de solo lectura, directorio de datos propio y sockets Wayland y audio necesarios. Evitar exponer el directorio personal, D-Bus general y sockets X11. La prueba inicial comprobó únicamente el espacio de nombres de red, con solo loopback. Si la prueba conjunta con WebKitGTK falla, revisar el diseño antes de ejecutar contenido importado. [Esquemas WebKitGTK](https://webkitgtk.org/reference/webkit2gtk/stable/method.WebContext.register_uri_scheme.html) · [Contexto y datos WebKitGTK](https://webkitgtk.org/reference/webkit2gtk/2.38.1/ctor.WebContext.new_with_website_data_manager.html)
4. **Política común.** Bloquear navegación a otros orígenes, red externa, ventanas emergentes, descargas, selectores web, permisos de cámara, micrófono, ubicación y portapapeles. No registrar puentes JavaScript a APIs nativas. Incluir cabeceras restrictivas de origen cuando lo permita el cargador. Probar recursos secundarios, redirecciones y peticiones iniciadas por scripts, además de enlaces. Registrar un código de error local sin rutas privadas, consultas, contenido de partida ni telemetría. [Riesgos de puentes nativos](https://developer.android.com/privacy-and-security/risks/insecure-webview-native-bridges)

## Controles y ciclo de vida

| Función | Android | Linux |
| --- | --- | --- |
| Entrada y escala | Tacto y pulsaciones nativas, viewport del dispositivo, barras del sistema y rotación. | Teclado, puntero, enfoque y redimensionado GTK. Los atajos del reproductor deben tener prioridad solo donde corresponda. |
| Pantalla completa | Acción nativa con regreso visible y prueba al volver de segundo plano. | Cambio GTK con salida accesible al teclado. |
| Audio | Empezar después de un gesto y comprobar suspensión, reanudación y estado de audio. | Aplicar la misma regla y verificar codecs con GStreamer en el entorno objetivo. |
| Fallos y cierre | Cerrar la vista, soltar recursos y manejar la salida del renderizador. Pausa cooperativa, según lo que permita el proveedor. | Cerrar ventana, sesión y proceso auxiliar. Reportar terminación anormal de WebKit. |
| Guardado | Verificar persistencia y separación de perfiles con dos orígenes. | Verificar persistencia y separación de rutas de datos con dos juegos. |

Se priorizan HTML, CSS, JavaScript local, Canvas 2D, fuentes y audio de prueba. WebGL, WebAssembly, workers, codecs adicionales, autoplay y juegos que necesiten CDN quedan sujetos a validación. Chromium y WebKit pueden comportarse de forma distinta aunque carguen el mismo documento. Los ajustes de pausa y guardado solo se expondrán cuando la sesión los pueda mantener. [Ajustes multimedia de Android](https://developer.android.com/reference/android/webkit/WebSettings) · [Ajustes multimedia de WebKitGTK](https://webkitgtk.org/reference/webkit2gtk/2.38.5/property.Settings.media-playback-requires-user-gesture.html) · [Terminación del proceso WebKit](https://webkitgtk.org/reference/webkit2gtk/stable/signal.WebView.web-process-terminated.html)

## Activación bajo demanda

El BLOQUE 10 debe permitir una activación explícita de desarrollo para ensayar el adaptador. La distribución queda para el BLOQUE 12. En Android se propone usar el motor del sistema y código de integración incluido en la app, con activación opcional identificada por el administrador. El proveedor se actualiza por su canal del sistema. La desactivación del adaptador se separa de borrar guardados o desinstalar el proveedor. Esto requiere aprobación porque el código Kotlin y AndroidX viajarían con el APK. En Linux se propone empaquetar el auxiliar por separado y depender de WebKitGTK del sistema. Definir de forma explícita qué actualiza y retira el administrador en cada plataforma.

## Plan de pruebas del BLOQUE 10 y del BLOQUE 11

Se crearán muestras propias y locales. La escena inicial mostrará texto, imagen y fuente, tocará un WAV corto generado para la prueba y aceptará interacción por toque, teclado y ratón. Habrá una segunda carpeta con otro origen para comprobar persistencia y separación. Una tercera variante cubrirá recursos ausentes, navegación bloqueada, solicitudes fuera del origen y permisos denegados. No se descargaron juegos durante esta evaluación.

| Prueba | Resultado exigido |
| --- | --- |
| Apertura y recursos | La entrada y las rutas relativas se cargan. Un recurso ausente produce un error visible y el reproductor sigue respondiendo. |
| Seguridad | Ningún recurso fuera de la raíz se entrega. Navegación externa, red, ventanas extra y permisos se deniegan con el motor activo. |
| Controles | Van bien cambio de tamaño, regreso y pantalla completa; el audio inicia tras un gesto y se detiene al cerrar. |
| Aislamiento | Guardar en un juego y reabrirlo conserva el dato. Un segundo juego no lo puede leer. |
| Ciclo de vida | Tras cerrar y reabrir no quedan procesos, vistas, sesiones ni archivos de staging activos. Los fallos informan sin bloquear la biblioteca. |

El resultado de este bloque es una propuesta de arquitectura y pruebas. La aprobación de Android primero y de las condiciones anteriores es el punto de control antes de escribir el runtime.
